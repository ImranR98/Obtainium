# Obtainium PR Review and Merge

Reviews every open PR in `ImranR98/Obtainium`, reports which are safe to merge,
fixes mechanical issues, merges approved PRs one at a time, and closes approved
rejections. Nothing is merged, pushed, commented, or closed without explicit user
consent in the current conversation.

`scripts/collect.mjs` only gathers facts. It computes no verdicts. Read
`references/criteria.md` and apply it yourself during the judgment pass.

## Guardrails (non-negotiable)

- Never merge, push, comment, or close without the user's explicit consent for that action.
- Consent is per batch, not per PR: report first, ask once, then act on the approved set.
- Process approved actions in ascending PR number. Merge one PR at a time and verify each merge.
- Never force-push. Never amend or rewrite a contributor's commits; add a fix commit instead.
- Never delete branches. Never merge with `--squash` or `--rebase`; use `--merge` (merge commit).
- Never push to `main` directly. If a fix cannot be pushed to the contributor's branch, stop and report.
- Re-check the PR head SHA immediately before merging; skip any PR whose head changed since review.
- Re-check mergeability immediately before merging; skip conflicts and stop the batch on the first failure.
- Every GitHub comment posted by the agent must end with a divider and this exact line:

  ```text
  ---

  Note: This comment was generated by an LLM, with manual review and approval.
  ```

- Work from the repo root. Use `/tmp/opencode/obtainium-pr-review/` for facts, diffs,
  logs, and the ledger; never write review state into the repository.
- The repo's only PR CI is translation JSON validation. Do not treat "no checks" as a
  failure, but do not merge code without the local gates in `references/criteria.md`.
- Never change the version in `pubspec.yaml`, and never advance the `.flutter` submodule.
  The latter belongs only to the `dependency-updates` skill.

## Merge-ready definition

A PR is merge-ready only if all of the following hold:

- Open, not a draft, base `main` (unless it is an explicitly requested internal PR),
  mergeable, and not an abandoned stale draft.
- The diff matches the title, body, and linked issue. No unrelated changes, no generated
  artifacts, no version bump, no `.flutter` pointer, no secrets.
- Translation-only PRs pass the structural checks in `references/criteria.md`: valid JSON,
  key parity and order with `en.json`, matching placeholders/plurals, no dropped keys, no
  translated values regressing to English, and `standardize.mjs` produces no diff.
- Code PRs pass `flutter pub get`, `flutter analyze`,
  `dart format --set-exit-if-changed .`, and `flutter test`; a PR that changes dependencies
  must also keep `pubspec.lock` consistent (`pub get --enforce-lockfile`); they include tests
  for logic and UI changes unless the change genuinely cannot be tested.
- User-facing strings use `tr()`/`plural()` with keys in `assets/translations/en.json`, and
  the locale files have been standardized.
- Android/native/dependency changes build (`flutter build apk --flavor normal`), and are
  reviewed for permissions, intents, installer commands, URLs, credentials, and secrets.
- Behavior changes are verified on an attached emulator/device with `./tool/e2e.sh` or a
  targeted manual/ADB check. If no device is attached, ask the user; do not claim
  verification you did not perform.
- New sources meet the source criteria in `references/criteria.md` (not already possible
  with HTML, reliable version and APK extraction, generally applicable, tested, documented).
- Docs are updated when architecture, conventions, or developer workflows change.

Everything else goes in `fixable`, `needs-review`, `needs-author`, or `close`. You may
override your own classification with judgment, but say why.

## Phase 0 — Preflight

- Run from the repo root. Inspect `git status --porcelain`; never stash or stage unrelated
  work. A dirty tree is safe for read-only collection, `gh` merges, and `gh` closes. For
  any local fix, use a temporary worktree (or stop and ask) so the user's work is untouched.
- Confirm tooling: `gh auth status`; repo slug via
  `gh repo view --json nameWithOwner -q .nameWithOwner` (use it as `$REPO`); Flutter and
  Android SDK per `AGENTS.md`. Use `./.flutter/bin/flutter` when present.
- Create a scratch ledger at `/tmp/opencode/obtainium-pr-review/<YYYY-MM-DD>-ledger.md`.
  Record every decision, approved comment, close/merge action, fix commit, and verification
  result. Long runs will be compacted; the ledger is the memory.
- Check for a device only when a code PR needs runtime verification: `adb devices` via the
  SDK resolved from `AGENTS.md`. If nothing is attached, ask the user to launch an emulator
  (list AVDs with `<sdk>/emulator/emulator -list-avds`) and do not proceed to device
  verification without one.

## Phase 1 — Collect facts

```bash
node .agents/skills/review-and-merge-prs/scripts/collect.mjs prs
node .agents/skills/review-and-merge-prs/scripts/collect.mjs prs --author <login> --limit 50
node .agents/skills/review-and-merge-prs/scripts/collect.mjs prs --pr 3535 --pr 3524 --print-digest
node .agents/skills/review-and-merge-prs/scripts/collect.mjs prs --skip-diff   # faster, less detail
node .agents/skills/review-and-merge-prs/scripts/collect.mjs prs --prs 3480,3482,3483
```

It writes `/tmp/opencode/obtainium-pr-review/prs.json`, `prs.json.digest.txt`, and
`diffs/<n>.diff`, and prints the paths. The digest has one block per PR with scope,
mergeability, draft/base/head, checks, linked issues, age, overlap, and flags. Read the
digest in batches with the Read tool (offset/limit) or filter it with Grep. Do not read the
full JSON into context; open it only for PRs that need detail. Use `gh pr view <n>` and
`gh pr diff <n>` when a semantic check needs the body, comments, or full diff.

## Phase 2 — Classify and judge

Read `references/criteria.md` and apply it to every PR using the digest facts:

- **Kind**: translation-only, code, docs, mixed, or internal. Internal means the maintainer's
  own PR (author is the repo owner, or the head branch is `dev`). List internal PRs but do
  not review or merge them unless the user asks.
- **Translation-only**: check the changed locale path, key parity/order, placeholders,
  plurals, regressions, and the `en.json` ownership rule.
- **Code**: inspect the diff, linked issue, tests, docs, strings, and security-sensitive
  paths. Run the verification gates for likely merge candidates.
- **Source changes**: check the source criteria; verify at least one real URL produces a
  version and APK, using the app or a focused test.
- **Android/native/installer changes**: review command construction, quoting, package/user
  IDs, permissions, intent filters, path handling, and URLs; build before merging.
- **Docs/metadata**: check accuracy against the code and current app behavior.
- **Overlaps**: same-file translation batches and duplicate linked issues need an explicit
  merge order or a decision; do not blindly merge a conflicting pair.

Verify only plausible merge candidates. Do not burn time running the full gate suite on
obvious rejects, drafts, or conflicting PRs.

## Phase 3 — Report and get approval

Summarize in five buckets. Keep entries to one line; list concrete fixes for fixable PRs.

```markdown
## ✅ Ready to merge (N)
- #3524 Show updates for pseudo-versioned apps @ibrahim-iqbal — tests + analyze pass, no device needed

## 🔧 Fixable here (N)
- #3530 Update bs.json @Errudar — file is at the repo root; move to assets/translations/bs.json after key-parity check

## ⚠️ Needs your review (N)
- #3487 Root installer profile fix @wiyba — installer/root behavior, needs device verification

## 💬 Needs author changes (N)
- #3536 SHOW_APP_INFO @sybenx — behavior is plausible; needs a test or emulator evidence and a docs check

## ❌ Suggest close (N)
- #2149 Multi-device sync @Fmstrat — draft, conflicting, no activity since ...
```

Then ask for consent with the question tool: `Merge all ready (recommended)`,
`Fix then merge fixable`, `Close the suggested rejects`, `Pick PRs manually`, `Cancel`.
Record exactly which PR numbers were approved for merge, fixing, closing, or commenting.
Do not act on anything not approved.

## Phase 4 — Fix and merge approved PRs

Process the approved set in ascending PR number. For each PR:

1. Re-fetch: `gh pr view <n> --json state,isDraft,mergeable,mergeStateStatus,headRefOid,maintainerCanModify,baseRefName`.
   Abort this PR if closed, draft, conflicting, based on the wrong branch, or its head changed
   since the report.
2. If a fix was approved, apply it in a temporary worktree (or a clean checkout). Use only
   the mechanical fixes in `references/criteria.md`. Never edit non-English locale values by
   hand; run `standardize.mjs` for structural fixes. Add a fix commit; never amend.
3. Re-run the relevant verification (`scripts/verify.sh <n>` or the commands in
   `references/criteria.md`). Do not merge if verification fails.
4. Push the fix only if `maintainerCanModify` is true and the user approved fixing. Inspect
   the upstream remote first (`git rev-parse --abbrev-ref --symbolic-full-name @{u}`); push
   the branch without force. If the push is rejected or edits are disabled, stop and report.
5. Merge:

   ```bash
   gh pr view <n> --repo "$REPO" --json state,mergeable,mergeStateStatus,headRefOid
   gh pr merge <n> --repo "$REPO" --merge --match-head-commit <headRefOid> --delete-branch=false
   gh pr view <n> --repo "$REPO" --json state,mergedAt,mergeCommit
   ```

   Confirm `state == "MERGED"`. Pause about a second between merges. On any failure (conflict,
   rate limit, protected state), stop the loop and report progress.
6. For same-file translation batches, merge one, then re-check the remaining PRs; if the
   next one conflicts, stop and report rather than resolving it without consent.

## Phase 5 — Close approved rejections

Only after explicit consent, per PR:

```bash
gh pr close <n> --repo "$REPO" --comment "<reviewed text + footer>"
```

PRs have no close reason on GitHub, so the comment carries the reason. Use the maintainer's
style and cite the concrete evidence:

- **Superseded**: name the merged PR/commit and what it covers.
- **Duplicate**: name the canonical PR and the shared issue/scope.
- **Invalid**: cite the rule (version bump, misplaced file with no new content, wrong target,
  already possible with HTML, unsupported source, security/design decision).
- **Stale**: state the last relevant activity and the 8-week window; invite the author to
  reopen with a rebase if they return.

Do not close a PR that is merely fixable or needs author changes. Do not delete branches.
Do not add labels by default; `duplicate` is unused in this repo. If the user asks for
labels, use only existing repo labels.

## Phase 6 — Optional author feedback

If the user approves comments for PRs that are not being merged or closed, post one concise
comment with the specific requested change and the footer. Do not post a formal review unless
the user asks. Do not comment on internal PRs. Record every comment in the ledger.

## Phase 7 — Final report

List:

- Merged PRs with merge commit hashes and the verification performed.
- Closed PRs with the reason.
- Fix commits (hash, subject) and whether they were pushed or are local.
- PRs left open with the blocking reason and suggested next step (author change, rebase,
  device verification, maintainer decision, wait).
- Anything that remains unverified and why. Never claim a verification you did not perform.

## Gotchas

- The working tree may be dirty with unrelated user work. Use temp worktrees for local
  verification and never stage or stash unrelated files.
- Translation PRs often share one locale file. Detect overlaps in the digest and merge in
  ascending order with a re-check between each.
- A complete translation file can be added at the repo root by mistake. That is not a
  simple move until the content is compared with the existing locale; flag it instead of
  overwriting community translations blindly.
- Code PRs with no tests may still be valid, but behavior changes need device evidence.
  Installer/root/Shizuku changes cannot be fully verified without the relevant environment;
  say so and leave them for the user when required.
- `gh pr close` has no `--reason`; use `--comment`. `gh pr merge` defaults can delete
  branches, so pass `--delete-branch=false`.
- Merging a PR whose body says `Fixes #N` closes the issue automatically. That is the repo's
  existing convention; do not manually close linked issues.
- The `to check` and `needs follow up` labels are for issues, not PRs. Do not apply them here.
